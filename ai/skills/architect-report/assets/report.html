A provider timeout is the only checkout case that leaves work behind

A successful charge and a declined card both finish inside one request. A timeout stores a pending order and hands the charge to a background retry.

Every case diverges after the charge call

Checkout API is the only service that talks to the payment provider. What it stores, sends and queues depends on the provider's answer.

Happy path. The provider accepts the charge. Checkout API writes the order and asks Notifier for a receipt.

Card declined. The provider refuses the charge. Nothing is written; the shopper sees the error and can change the card.

Provider timeout. No answer arrives in time. Checkout API writes the order as pending and queues a retry.

Components

Checkout API

Validates the cart, calls the provider once per request, and decides what to store. The only caller of the payment provider.

Payment Provider

External service. Answers accepted or declined, or does not answer within the timeout.

Orders DB

Holds one row per order. A declined charge creates no row.

Retry Queue

Receives a job only after a timeout. Retries the charge with backoff, then gives up.

Paid is the only goal state

The same three cases, seen as the states one order passes through.

Happy path. Pending, Authorized, Paid.

Card declined. Pending, then Declined.

Provider timeout. Pending, Retrying, then Paid if a retry succeeds or Failed after the last try.

A timeout holds the request open until the limit

The shopper waits for the whole charge timeout before seeing anything. The work after it is short.

Two questions are still open

Decided

  • Checkout API is the only caller of the payment provider.
  • A declined charge stores nothing.
  • A timeout stores a pending order and retries in the background.

Open

  • Who is told when an order reaches Failed?
  • Can a retry charge a card twice if the first call succeeded late?

Risk. Until the second question is answered, a late success plus a retry could charge twice.
